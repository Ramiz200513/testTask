# Аванс по договору: отчёт по расчётам с подрядчиками

Программа строит отчёт на выбранную дату по выгрузке из `data/` (договоры, работы, платежи):

- по каждой работе: цена, сколько выплачено и сколько осталось оплатить;
- по каждому договору: итоги, переплата, платежи в очереди;
- расшифровку: какой платёж за какие работы зачтён;
- замечания: что в выгрузке изменилось уже после даты отчёта, где не сходятся суммы.

## Запуск

Нужен Python 3.9 или новее. Зависимостей нет, только стандартная библиотека. Команды выполняются
из корня репозитория.

```bash
python -m advance_report --date 10.11.2026
```

Дату можно писать как `10.11.2026` или как `2026-11-10`. Отчёт строится на конец этого дня.

| Параметр | Что делает |
|---|---|
| `--date` | Дата отчёта, обязательный параметр. |
| `--data ПАПКА` | Папка с `contracts.csv`, `works.csv`, `payments.csv`. По умолчанию `./data`. |
| `--format table\|csv\|json` | `table` — таблица для чтения (по умолчанию), `csv` — для Excel, `json` — для программ. |
| `-o, --output ФАЙЛ` | Записать отчёт в файл (UTF-8; CSV — с BOM, чтобы Excel сразу понял кириллицу). |
| `--allocation fifo\|pro-rata` | Как раскладывать платежи без привязки по работам (см. ниже). По умолчанию `fifo`. |

Примеры:

```bash
python -m advance_report --date 10.11.2026 --format csv -o report.csv
```

```bash
python -m advance_report --date 10.11.2026 --allocation pro-rata
```

```bash
python -m advance_report --date 2026-11-10 --data /путь/к/другой/выгрузке --format json
```

Коды выхода:
- `0` — отчёт построен;
- `1` — в данных ошибки, все они перечислены в stderr с файлом и номером строки;
- `2` — неверные параметры, например несуществующая дата.

> **Windows.** В консоли PowerShell и cmd отчёт выводится нормально. Если перенаправить вывод в
> файл через `>`, Windows запишет его в однобайтовой кодировке. Для файла лучше `-o report.txt`:
> так он сохранится в UTF-8.

## Как считается

Подробно с вариантами — в [DECISIONS.md](DECISIONS.md). Коротко:

1. **Состояние на дату восстанавливается по датам событий,** а не берётся из поля `status`: тот
   дан на момент выгрузки. Поэтому на 10.11:
   - W-23 ещё не принята (её приняли 11.11);
   - P-8 не учтён (его оплатили 12.11);
   - P-2 не учтён (его вернули 10.09);
   - P-4 не выплачен, он только в очереди.
2. **Привязанный к работе платёж** идёт в эту работу, но не больше её цены. Излишек уходит в общие
   платежи договора.
3. **Платежи без привязки** (`fifo`) сначала закрывают принятые работы в порядке приёмки, так
   погашаются долги по ст. 319.1 ГК РФ. Что сверх, становится авансом за непринятые работы и
   делится пропорционально цене. Режим `pro-rata` вместо этого делит деньги на все действующие
   работы одной долей.
4. **Отменённая работа** к оплате не идёт.
5. **Переплата** показывается отдельно, «выплачено» по работе никогда не больше её цены.
6. **Деньги** считаются в целых копейках, без float. Доли делятся методом наибольшего остатка,
   поэтому всё сходится до копейки. Отчёт сам сверяет инварианты и упадёт, если копейка потеряется.

Итоги по договору от режима раскладки не зависят, от него зависит только деление между работами.

## Что нашлось в данных

Эти пункты я вынес в записку бухгалтеру как вопросы.

- **P-4 «Остаток» 150 000, в очереди, договор D-1.** Подрядчику уже выплачено 315 000, а принятые
  работы стоят 300 000. Даже по схеме «50% аванс + 50% после приёмки», с учётом отменённой W-13,
  доплатить нужно не больше 100 000.
- **Отменённая W-13.** Аванс 50% по D-1 (300 000) считали от 600 000 — с учётом W-13, которую
  потом отменили.
- **P-3 «Материалы для съёмки» 15 000.** Непонятно, в счёт цены W-14 или сверх неё.
- **P-7 «Доплата» 5 000, договор D-2.** С 12.11 по D-2 выплачено 95 000 при договоре на 90 000,
  то есть переплата 5 000 (см. [examples/report_2026-11-16.txt](examples/report_2026-11-16.txt)).

## Тесты

```bash
python -m unittest -v
```

74 теста, только стандартная библиотека, проверены на Python 3.11 и 3.14. Что покрыто:

- **Деньги.** Разбор сумм, отказ от сумм с 3 знаками после запятой, деление до копейки.
  Свойства проверены на 2000 случайных наборов.
- **Состояния на дату.** Границы «включительно», возврат до и после даты, очередь.
- **Раскладка.** Порядок приёмки, приёмка в один день, излишек привязанного платежа, платёж к
  отменённой работе, переплата.
- **Чтение данных.** BOM, CRLF, запятая в кавычках, файл из русского Excel (`;` и cp1251), все
  ошибки сразу без ложных каскадных, предупреждения.
- **Эталон по `data/`.** Расчёт на 10.11, 05.09 и 16.11, числа посчитаны вручную. На 05.09 P-2
  ещё учтён, а D-2 не подписан. На 16.11 у D-2 переплата.
- **Инварианты.** 300 случайных выгрузок в обоих режимах.
- **CLI.** Форматы, коды выхода.

Чтобы убедиться, что тесты ловят ошибки, я по очереди вносил в код 11 правдоподобных багов: дата
не включительно, возврат не учитывается, статус из выгрузки, обратный порядок приёмки, потеря
копеек, оплата отменённой работы, очередь как выплата, потеря излишка и другие. Каждый баг уронил
тесты.

Кроме того, отдельный агент сделал независимое ревью кода. Он прогнал 3000 случайных выгрузок
через все форматы и нашёл пять пограничных случаев:
- заблокированный файл давал трейсбек;
- платёж до подписания договора выпадал из отчёта;
- работа «принята, потом отменена» теряла дату приёмки;
- текст в CSV мог исполниться в Excel как формула;
- перенос строки в названии ломал таблицу.

Все пять исправлены и покрыты тестами (`tests/test_review_fixes.py`). На данных из `data/` ни один
из них цифр не менял.

## Устройство

```
advance_report/
  money.py       копейки: разбор, формат, деление пропорционально с лимитами
  dates.py       даты 2026-11-10 и 10.11.2026
  model.py       договор, работа, платёж - как в FORMAT.md
  loader.py      чтение CSV и проверка: все ошибки сразу, с номерами строк
  asof.py        состояние работы и платежа на дату отчёта
  allocation.py  раскладка платежей по работам (fifo / pro-rata) и расшифровка
  report.py      строки, итоги, сверка инвариантов, замечания
  render.py      таблица, CSV, JSON
  cli.py         параметры командной строки
tests/           unittest
examples/        готовые отчёты на 10.11.2026 (и на 16.11 - для сравнения)
```

## Что не сделано и что бы я сделал дальше

- **Получить ответы бухгалтера** (записка, пункты 4–8) и поправить допущения. Каждое допущение
  описано в DECISIONS.md вместе с тем, что изменится в отчёте.
- **Хранить условия договора в данных:** схему зачёта аванса и процент аванса. Сейчас схема
  выбирается ключом на весь отчёт. Если договоры работают по разным схемам, это стоит хранить в
  `contracts.csv` или в отдельном файле условий.
- **Учитывать дату выгрузки.** В данных её нет. Отчёт на дату позже выгрузки молча считает, что
  после выгрузки ничего не происходило. Стоит передавать дату выгрузки и предупреждать.
- **Изменения договора во времени** (допсоглашения), частичные возвраты, корректировки. В формате
  их нет. Если появятся, понадобится журнал событий вместо статусов.
- **XLSX с форматированием** вместо CSV, если бухгалтеру так удобнее.
